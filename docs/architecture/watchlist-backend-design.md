# Module: watchlist

**Status:** design proposal only. Do not implement code or migrations from this document without a follow-up implementation task.

Watchlist is the planned backend boundary for saved security monitoring and price-threshold alerts. The first release supports:

- `PERSONAL` watchlists owned by one user
- `PORTFOLIO` watchlists attached to one portfolio
- market-price thresholds only
- crossing-based alerts with cooldown and re-arm behavior

Watchlist must not implement NAV, AUM, valuation, risk, or portfolio-performance thresholds in the first release.

## Module Boundary

Watchlist should be a standalone module at `backend/internal/watchlist` because it owns user intent, alert rules, alert state, and acknowledgement workflows. Those concerns do not belong in provider-facing market data or investment accounting.

Watchlist owns:

- watchlist item membership for canonical securities
- personal and portfolio scope rules
- threshold rule validation and lifecycle
- alert evaluation state, including breached/non-breached transitions
- persisted alert events and acknowledgement state
- alert idempotency keys
- Watchlist-specific audit event emission
- Watchlist HTTP routes, DTOs, use cases, repositories, permissions, and evaluator worker

Watchlist must reuse:

- `reference_data` for canonical securities from `securities_master`
- `market_data` only as a quote provider dependency
- `investment` only for portfolio existence and portfolio-to-data-scope resolution where needed
- IAM/permissions for function and data permission checks
- `notification` for alert delivery
- `audit` for immutable audit events
- `workflow` business-day scheduling patterns if scheduled evaluation needs business-day awareness

`/api/v1/market-data/screen/watchlist` is not the real Watchlist domain. It is a market-data screen feed that returns active canonical securities joined to latest snapshot data for the Market Data UI. Do not extend that route into item management, alert rules, portfolio scope, acknowledgement, or notification behavior.

Layer guidance:

- `domain/entity`: `WatchlistItem`, `ThresholdRule`, `AlertEvent`, state enums, validation invariants.
- `domain/repository`: repository interfaces for items, rules, alert events, evaluation cursors.
- `domain/service`: pure crossing logic, breach predicates, cooldown/re-arm decisions.
- `application/command`: create/update/delete item, create/update threshold, acknowledge alert, manual evaluate.
- `application/query`: list watchlists and list alert events with scope filtering.
- `application/service`: evaluator orchestration, permission-aware use cases, notification/audit sequencing.
- `infrastructure/persistence`: Postgres repositories and transaction helpers.
- `infrastructure/adapter`: ports to reference data, market data quote provider, investment portfolio scope resolver, notification, and audit.
- `transport/http`: chi routes, request/response DTOs, httputil response envelope usage.
- `permission`: permission code catalog implementing the existing module permission catalog pattern.
- `jobs`: scheduled evaluator worker. Use workflow scheduler patterns if the job must run only on business days or with business-day cutoffs.

Expected wiring in `backend/cmd/server/main.go`:

- construct `watchlist.NewModule(...)` after `referenceDataModule`, `marketDataModule`, `investmentModule`, `notificationModule`, and `auditModule` are available
- inject the IAM module for function and data checks
- inject `referenceDataModule.Resolver()` or a narrow security lookup port
- inject `marketDataModule.QuoteProvider()` as the only market-data dependency
- inject an investment portfolio access/scope resolver if portfolio IDs must be resolved before IAM data checks
- inject a Watchlist notification adapter backed by the notification module
- call `watchlistModule.RegisterRoutes(r)` inside the authenticated `/api/v1` group
- start the evaluator worker with the server scheduler context if background evaluation is enabled

## Data Model Proposal

This section documents proposed tables only. Do not create migrations yet.

### `watchlist_items`

Purpose: one canonical security tracked in either a personal or portfolio-scoped watchlist.

Recommended fields:

| Field | Notes |
| --- | --- |
| `id uuid primary key` | Generated by backend. |
| `scope_type text not null` | `PERSONAL` or `PORTFOLIO`. |
| `owner_user_id uuid null` | Required for `PERSONAL`; for `PORTFOLIO`, may store creator/owner for audit and default notifications. |
| `portfolio_id uuid null` | Required for `PORTFOLIO`; null for `PERSONAL`. |
| `security_id uuid not null` | References canonical `securities_master`. Store canonical ID, not provider symbol. |
| `display_order integer null` | Optional stable ordering. |
| `pinned boolean not null default false` | UI preference, still backend-owned state. |
| `note text null` | Optional user note. |
| `status text not null default 'ACTIVE'` | Recommended: `ACTIVE`, `DISABLED`. |
| `created_by uuid not null` | Actor that created the row. |
| `updated_by uuid null` | Last actor. |
| `deleted_by uuid null` | Actor that soft-deleted the row. |
| `created_at timestamptz not null` | UTC. |
| `updated_at timestamptz not null` | UTC. |
| `deleted_at timestamptz null` | Soft-delete marker. |

Scope constraints:

- `PERSONAL`: `owner_user_id is not null` and `portfolio_id is null`
- `PORTFOLIO`: `portfolio_id is not null`; `owner_user_id` may be null or may store creator

Recommended unique constraints:

- active personal item uniqueness: `(scope_type, owner_user_id, security_id)` where `scope_type = 'PERSONAL' and deleted_at is null`
- active portfolio item uniqueness: `(scope_type, portfolio_id, security_id)` where `scope_type = 'PORTFOLIO' and deleted_at is null`

Recommended indexes:

- `(owner_user_id, status)` where `deleted_at is null`
- `(portfolio_id, status)` where `deleted_at is null`
- `(security_id)` where `deleted_at is null`
- `(scope_type, updated_at desc)` where `deleted_at is null`

Soft delete:

- `DELETE /watchlists/items/{id}` should set `deleted_at`, `deleted_by`, `updated_at`, and `status = 'DISABLED'`.
- Threshold rules under a deleted item should be treated as inactive even if their own `status` remains `ENABLED`.

- `metric_type = 'MARKET_PRICE'`
- `direction in ('ABOVE', 'BELOW')`
- `threshold_value > 0`
- `cooldown_minutes >= 0`
- `status in ('ENABLED', 'DISABLED')`
- `last_state in ('UNKNOWN', 'NON_BREACHED', 'BREACHED')`
- unique active duplicate guard: `(watchlist_item_id, metric_type, direction, threshold_value)` where `deleted_at is null`

Recommended indexes:

- `(status, last_evaluated_at)` where `deleted_at is null`
- `(watchlist_item_id)` where `deleted_at is null`
- `(last_state, status)` where `deleted_at is null`

Soft delete:

- Prefer `deleted_at` plus `status = 'DISABLED'`.
- Disabled or deleted rules must not evaluate or create alerts.

- `direction in ('ABOVE', 'BELOW')`

- `(owner_user_id, created_at desc)` where `scope_type = 'PERSONAL'`
- `(portfolio_id, created_at desc)` where `scope_type = 'PORTFOLIO'`

- `(security_id, created_at desc)`

Alert events should not be hard-deleted. They are operational history and support audit review.

## API Design Proposal

All endpoints live under `/api/v1`, are authenticated, and should use the existing `httputil.SuccessResponse` and `httputil.ErrorResponse` envelopes.

### `GET /api/v1/watchlists`

Purpose: list watchlist items visible to the current actor, with optional threshold summaries and latest quote snapshots.

Permission code: `WATCHLIST_VIEW`.

Scope rules:

- `PERSONAL`: return only rows where `owner_user_id = actor_id`, unless `WATCHLIST_ADMIN` explicitly allows cross-owner access.
- `PORTFOLIO`: require portfolio data permission for each returned portfolio row.
- If both personal and portfolio rows are requested, apply each rule independently.

Request shape:

- query: `scope_type`, `portfolio_id`, `security_id`, `include_disabled`, `include_thresholds`, `limit`, `offset`

Response shape:

- `items[]`: item ID, scope, owner/portfolio IDs, security descriptor, status, pinned, note, threshold summaries, optional quote snapshot
- `total`, `limit`, `offset`

Important error cases:

- `400` invalid query values
- `403` forbidden portfolio or cross-owner personal scope
- `500` repository failure

### `POST /api/v1/watchlists/items`

Purpose: create a watchlist item and optionally create initial market-price threshold rules.

Permission code: `WATCHLIST_MANAGE`.

Scope rules:

- `PERSONAL`: ignore any supplied `owner_user_id`; set owner to authenticated actor.
- `PORTFOLIO`: require `portfolio_id` and verify actor has portfolio data permission.

Request shape:

- body: `scope_type`, `portfolio_id`, `security_id`, `pinned`, `note`, `threshold_rules[]`
- threshold rule body: `direction`, `threshold_value`, `currency`, `cooldown_minutes`, `status`

Response shape:

- created item with threshold rules and security descriptor

Important error cases:

- `400` invalid request body or invalid threshold
- `403` forbidden scope
- `409` duplicate active item for same scope/security
- `422` invalid or inactive security

### `PATCH /api/v1/watchlists/items/{id}`

Purpose: update item metadata and threshold rule definitions for an existing item.

Permission code: `WATCHLIST_MANAGE`.

Scope rules:

- Resolve the item first, then enforce personal owner or portfolio data permission before returning any business details.
- For portfolio items, data permission is required even if the actor created the item.

Request shape:

- path: `id`
- body: partial update for `pinned`, `note`, `status`, and threshold rule upserts/updates
- threshold updates should include `id` when updating an existing rule

Response shape:

- updated item with active threshold rules

Important error cases:

- `400` invalid ID or invalid threshold
- `403` forbidden scope
- `404` item not found or soft-deleted
- `409` duplicate threshold rule
- `422` unsupported threshold metric

### `DELETE /api/v1/watchlists/items/{id}`

Purpose: soft-delete a watchlist item and stop future evaluation of its rules.

Permission code: `WATCHLIST_MANAGE`.

Scope rules:

- `PERSONAL`: actor must own the item unless `WATCHLIST_ADMIN` explicitly allows override.
- `PORTFOLIO`: actor must have portfolio data permission.

Request shape:

- path: `id`

Response shape:

- `204 No Content`

Important error cases:

- `400` invalid ID
- `403` forbidden scope
- `404` item not found

### `GET /api/v1/watchlists/alerts`

Purpose: list alert events visible to the actor.

Permission code: `WATCHLIST_VIEW`.

Scope rules:

- Personal alerts are visible to the owner only unless admin/audit rules explicitly allow access.
- Portfolio alerts require portfolio data permission.
- `WATCHLIST_ADMIN` may allow operational filtering across users only when explicitly granted.

Request shape:

- query: `scope_type`, `portfolio_id`, `security_id`, `rule_id`, `acknowledged`, `created_from`, `created_to`, `limit`, `offset`

Response shape:

- `items[]`: alert event, rule snapshot, security descriptor, acknowledgement state, stale quote fields, notification status
- `total`, `limit`, `offset`

Important error cases:

- `400` invalid query values
- `403` forbidden scope
- `500` repository failure

### `POST /api/v1/watchlists/alerts/{id}/acknowledge`

Purpose: acknowledge an alert event.

Permission code: `WATCHLIST_ALERT_ACK`.

Scope rules:

- Actor must be able to view the alert by the same personal/portfolio rules used by alert listing.
- Admin acknowledgement should require `WATCHLIST_ADMIN` or an explicit risk/audit policy.

Request shape:

- path: `id`
- body: optional `note`

Response shape:

- updated alert event with `acknowledged_by` and `acknowledged_at`

Important error cases:

- `400` invalid ID
- `403` forbidden scope
- `404` alert not found
- `409` alert already acknowledged

### `POST /api/v1/watchlists/evaluate`

Purpose: manually run evaluation for enabled rules. This is an operational endpoint, not the normal scheduler path.

Permission code: `WATCHLIST_EVALUATE`.

Scope rules:

- Manual evaluation can be narrowed by `scope_type`, `portfolio_id`, `security_id`, `item_id`, or `rule_id`.
- If a portfolio is supplied, require portfolio data permission unless the caller has an explicit operational override policy.
- Normal user roles should not receive this permission.

Request shape:

- body: `scope_type`, `portfolio_id`, `security_id`, `item_id`, `rule_id`, `dry_run`

Response shape:

- counts: `rules_evaluated`, `alerts_created`, `alerts_suppressed`, `rules_skipped`, `provider_failures`
- optional `results[]` for dry run or debugging

Important error cases:

- `400` invalid filters
- `403` missing function permission or forbidden portfolio scope
- `409` rule disabled when targeting one disabled rule
- `503` provider unavailable when no usable quote exists for a targeted evaluation

## Permission Model

Proposed function permission codes:

- `WATCHLIST_VIEW`: list visible watchlist items and alerts.
- `WATCHLIST_MANAGE`: create, update, and delete watchlist items and threshold rules.
- `WATCHLIST_ALERT_ACK`: acknowledge visible alert events.
- `WATCHLIST_EVALUATE`: manually trigger rule evaluation.
- `WATCHLIST_ADMIN`: optional operational override for cross-owner personal access and administrative filters.

Personal owner-only rules:

- A personal row must have `scope_type = 'PERSONAL'`, `owner_user_id = actor_id`, and `portfolio_id = null`.
- Do not allow a user to create or update a personal watchlist for another user through normal APIs.
- Cross-owner access requires explicit `WATCHLIST_ADMIN` or a dedicated audit use case.

Portfolio data-scope rules:

- A portfolio row must have `scope_type = 'PORTFOLIO'` and `portfolio_id` populated.
- Access is governed by portfolio data permission, not by `owner_user_id`.
- If IAM data permissions are stored at contract/fund scope rather than raw portfolio ID, Watchlist must resolve the portfolio to the correct data scope through a narrow investment port before calling IAM.
- Data permission checks must happen in the application service because portfolio ID may come from request body or loaded row, not only from URL params.

Admin/risk/audit behavior:

- `WATCHLIST_ADMIN` may allow admin/risk users to view or manage personal watchlists only if product/security explicitly wants that behavior.
- Portfolio-scoped admin/risk access should still honor portfolio data permission unless there is a separately approved global portfolio data policy.
- Audit exports should prefer the audit module and alert-event query paths that enforce either owner/scope checks or explicit audit permission.

IAM integration:

- Use existing function permission middleware for route-level codes.
- Use existing IAM data permission checks for portfolio scope.
- Fail closed when portfolio scope cannot be resolved.
- Seed new function codes through the module permission catalog in the implementation phase.

## Alert Evaluation Design

### State Machine

Rule state values:

- `UNKNOWN`: rule has never been evaluated.
- `NON_BREACHED`: latest usable price is on the safe side.
- `BREACHED`: latest usable price is on the breached side.

Recommended breach predicates:

- `ABOVE`: breached when `observed_price >= threshold_value`
- `BELOW`: breached when `observed_price <= threshold_value`

Evaluation transitions:

| Previous state | Current predicate | Action |
| --- | --- | --- |
| `UNKNOWN` | non-breached | Set `NON_BREACHED`; no alert. |
| `UNKNOWN` | breached | Set `BREACHED`; no alert because no crossing from known non-breached state occurred. |
| `NON_BREACHED` | non-breached | Keep `NON_BREACHED`; no alert. |
| `NON_BREACHED` | breached | Crossing. Create alert event if cooldown allows. |
| `BREACHED` | breached | Keep `BREACHED`; no repeated alert. |
| `BREACHED` | non-breached | Set `NON_BREACHED`; re-arm rule; no alert. |

Crossing-based behavior:

- Trigger only when a rule crosses from `NON_BREACHED` to `BREACHED`.
- Do not repeatedly notify while the observed price remains breached.
- Re-arm only after the price returns to the non-breached side.
- First evaluation from `UNKNOWN` seeds state and should not alert.

### Cooldown

- Each rule has `cooldown_minutes`, default 60.
- When a crossing occurs, create an alert only if `last_alerted_at` is null or outside the cooldown window.
- If a rule re-arms and crosses again inside cooldown, suppress notification and record the rule as `BREACHED`. The next alert requires another return to `NON_BREACHED` and a later crossing.
- `cooldown_minutes = 0` should be allowed only if product accepts high-frequency alerts; otherwise enforce a minimum in validation.

### Stale Quote Handling

- The evaluator should call the injected market-data quote provider. Watchlist must not call external market-data providers directly.
- If market-data returns a stale fallback quote that is still within the accepted stale window, evaluation may proceed and must persist `stale = true` and `stale_reason`.
- If the quote is stale beyond the accepted stale window, skip alert creation, keep prior rule state, return/record `ErrStaleQuote`, and emit `WATCHLIST_EVALUATION_FAILED`.
- Stale-triggered alert notifications must include stale context so recipients know the alert was based on fallback data.

### Provider Failure Behavior

- If the provider returns a usable quote, evaluate normally.
- If the provider chain fails but market-data returns a cached stale quote, follow stale quote handling.
- If no usable quote exists, do not change rule state and do not create an alert event.
- Record an evaluation failure audit event for targeted/manual evaluation and log worker failures for scheduled evaluation.
- Continue evaluating other rules when one security/provider fails.

### Idempotency

Recommended idempotency key format:

```text
watchlist:rule:<rule_id>:crossing:<direction>:bucket:<timestamp>
```

Guidance:

- `direction` is `ABOVE` or `BELOW`.
- `timestamp` should be a UTC bucket start, truncated to the rule cooldown window or the evaluator bucket used by the worker.
- Persist the key on `watchlist_alert_events` with a unique constraint.
- Pass the same key to the notification module so alert delivery is idempotent.
- Treat duplicate alert event or notification creation as success with `notification_status = 'SUPPRESSED'`, not as a failed business operation.

### Notification and Audit Sequencing

Recommended sequence for a crossing:

1. Load rule and item with row-level locking or equivalent concurrency protection.
2. Evaluate current quote and compute transition.
3. Insert `watchlist_alert_events` with idempotency key.
4. Update rule state, `last_alerted_at`, and observed quote fields in the same transaction when possible.
5. After persistence, call the notification adapter using the same idempotency key.
6. Update notification status if needed.
7. Record `WATCHLIST_ALERT_TRIGGERED` audit event.

Audit should also be recorded for create/update/delete, acknowledgement, and evaluation failures.

## Notification Integration

Watchlist must reuse the notification module. It must not write notification tables or email outbox tables directly.

Recommended Watchlist-side port:

```go
type WatchlistAlertNotifier interface {
    NotifyThresholdBreached(ctx context.Context, input WatchlistAlertNotificationInput) error
}
```

The implementation should live in an adapter backed by the notification module service. The notification event type should be the existing `ALERT_THRESHOLD_BREACHED`.

Recommended notification recipient rules:

- `PERSONAL`: notify `owner_user_id`.
- `PORTFOLIO`: first implementation should notify the creator/owner user if available, or an explicitly configured portfolio alert recipient list. Do not infer all users with portfolio data access as recipients without a product decision.
- Every recipient must be authorized for the underlying personal or portfolio scope at creation time.

Recommended notification context fields:

- `watchlist_item_id`
- `threshold_rule_id`
- `alert_event_id`
- `security_id`
- `portfolio_id`
- `observed_price`
- `threshold_value`
- `direction`
- `stale`
- `stale_reason`

Recommended notification metadata:

- `SourceModule`: `watchlist`
- `SourceType`: `watchlist_alert_event`
- `SourceID`: `alert_event_id`
- `EventType`: `ALERT_THRESHOLD_BREACHED`
- `IdempotencyKey`: alert event idempotency key
- `BusinessType`: `WATCHLIST_ALERT`
- `BusinessID`: `alert_event_id`
- `BusinessReference`: a stable alert reference if one is introduced
- `ActionURL`: frontend route to the alert detail or watchlist page when available

## Audit Events

Required audit actions:

- `WATCHLIST_ITEM_CREATED`
- `WATCHLIST_ITEM_UPDATED`
- `WATCHLIST_ITEM_DELETED`
- `WATCHLIST_THRESHOLD_CREATED`
- `WATCHLIST_THRESHOLD_UPDATED`
- `WATCHLIST_ALERT_TRIGGERED`
- `WATCHLIST_ALERT_ACKNOWLEDGED`
- `WATCHLIST_EVALUATION_FAILED`

Audit guidance:

- Record actor ID for user-driven actions.
- Use a system actor or null actor for scheduled evaluator actions, consistent with existing audit conventions.
- Include scope, portfolio ID, owner user ID, security ID, rule ID, and alert event ID in metadata where applicable.
- Do not include raw provider payloads or secrets.
- For failures, store typed error code and safe message only.

## Error Handling

Expected typed errors and HTTP mapping:

| Typed error | Meaning | HTTP mapping |
| --- | --- | --- |
| `ErrInvalidSecurity` | Security is missing, inactive, or not in `securities_master`. | `422 Unprocessable Entity` |
| `ErrDuplicateWatchlistItem` | Active item already exists for same scope/security. | `409 Conflict` |
| `ErrInvalidThreshold` | Direction, value, metric, currency, or cooldown is invalid. | `400 Bad Request` |
| `ErrForbiddenScope` | Actor cannot access personal owner or portfolio scope. | `403 Forbidden` |
| `ErrStaleQuote` | Quote is too stale for alert evaluation. | `409 Conflict` for targeted evaluation; skipped result in batch evaluation |
| `ErrProviderUnavailable` | No live or accepted stale quote is available. | `503 Service Unavailable` for targeted evaluation; skipped result in batch evaluation |
| `ErrAlertAlreadyAcknowledged` | Alert has already been acknowledged. | `409 Conflict` |
| `ErrRuleDisabled` | Targeted evaluation or update attempted on disabled/deleted rule. | `409 Conflict` |
| `ErrNotificationDuplicate` | Notification module suppressed duplicate by idempotency key. | `200 OK` with `notification_status = 'SUPPRESSED'` |

General mapping:

- malformed UUID or JSON: `400`
- missing authentication: `401`
- failed function permission: `403`
- not found after scope-safe lookup: `404`
- repository or unexpected errors: `500`

Handlers should not leak provider payloads, SQL details, or internal permission-resolution errors in response messages.

## Test Plan

Required tests:

- Domain unit tests for crossing logic:
  - `UNKNOWN` seeding does not alert
  - `NON_BREACHED` to `BREACHED` alerts
  - `BREACHED` to `BREACHED` does not repeat
  - `BREACHED` to `NON_BREACHED` re-arms
  - `ABOVE` and `BELOW` predicates
- Cooldown and re-arm tests:
  - crossing inside cooldown suppresses
  - crossing after cooldown alerts
  - cooldown alone does not alert without re-arm
- Repository tests:
  - personal uniqueness with soft delete
  - portfolio uniqueness with soft delete
  - alert event idempotency unique key
  - disabled/deleted rules excluded from evaluator queries
- API handler tests:
  - request validation
  - `httputil` success/error envelope shape
  - create/list/update/delete item flows
  - alert listing and acknowledgement
  - manual evaluation response counts
- Permission tests:
  - personal owner can view/manage own rows
  - personal non-owner denied
  - portfolio user with data permission allowed
  - portfolio user without data permission denied
  - optional admin behavior explicitly covered
- Evaluator worker tests:
  - provider quote success
  - stale quote accepted
  - stale quote rejected
  - provider unavailable continues other rules
